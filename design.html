1. Introduction, Pedagogical Context & Objectives

Academic Reference

Rather than treating the Internet of Things (IoT) as a single isolated technology, the IoT Demo System project is deliberately scoped to touch every tier of a production IoT stack — embedded firmware, short-range wireless networking, edge computing, cloud services, and a presentation client — so that students leave the course with practical, integration-level experience rather than single-layer siloed knowledge.

Students design, build, and operate a working, end-to-end IoT demonstration system over the course of the academic term. The learning objectives emphasize:

  • Configuring low-power ESP32-WROOM-32D microcontrollers with environmental and kinetic transducers under RTC deep sleep duty cycles.
  • Operating short-range Bluetooth Low Energy (BLE 5.0) GATT connections and advertising packets with rigorous battery budgeting.
  • Building a resilient Edge Gateway on Linux (Raspberry Pi 4 Model B) executing protocol translation and SQLite store-and-forward caching during network partitions.
  • Connecting securely to AWS IoT Core via mutual TLS (mTLS on port 8883), with serverless rule routing into DynamoDB and Lambda anomaly alerting.
  • Operating closed-loop reverse actuation from a native Android Mobile Application (Kotlin/Compose) and Web Operations Dashboard down to physical actuators.

3. Perception Layer — Hardware, Firmware & Power Architecture

🎛️ Open Perception Layer Firmware & Testing Console (perception.html) ↗

The perception tier constitutes the physical data acquisition frontier. In our design, field nodes utilize the Espressif ESP32-WROOM-32D microcontroller (with the Nordic nRF52840 evaluated as an alternative ultra-low-power BLE target). The ESP32 integrates dual Xtensa 32-bit LX6 cores operating up to 240 MHz, 520 KB SRAM, 4 MB external SPI flash, and a certified 2.4 GHz 802.11 b/g/n Wi-Fi + Bluetooth 5.0 (BLE) radio subsystem.

Figure 3. Prototype end-device assembly on solderless breadboard with environmental BME280/DHT22 transducer and status LEDs.

🔋 Power Optimization & Duty-Cycle Mathematical Model

Because constrained perception nodes are powered by a 3.7V 1200 mAh LiPo battery, continuous active radio listening (80–120 mA) would deplete the cell within 12–15 hours. The firmware instead operates an aggressive RTC-driven deep sleep duty cycle where average current draw is governed by:

I_avg = ((I_active * t_active) + (I_sleep * t_sleep)) / (t_active + t_sleep)

Where \(I_{\text{active}} \approx 80\,\text{mA}\) for \(t_{\text{active}} \approx 120\,\text{ms}\) (wake, sample I²C, broadcast BLE frame), and \(I_{\text{sleep}} \approx 10\,\mu\text{A}\) during deep sleep.

5 seconds 2.34% 1.88 mA 26.5 Days (~3.8 Weeks) Rapid laboratory testing and dynamic motion tracking.
10 seconds (Standard) 1.18% 0.95 mA 52.6 Days (~7.5 Weeks) Standard IoT demo baseline (balanced latency & power).

5. Edge Gateway Layer Hardware & Store-and-Forward Engine

📟 Open Edge Gateway Operations Console (gateway.html) ↗

The edge gateway bridges the constrained local BLE network and the wide-area cloud IP network. It runs a headless Linux environment managing concurrent BLE GATT central connections, translating binary sensor frames into structured JSON payloads, maintaining a resilient SQLite store-and-forward buffer during WAN disconnects, and authenticating to AWS IoT Core over mutual TLS 8883.

6. AWS Cloud Backend Architecture & Serverless Pipeline

☁️ Open AWS Cloud Operations Console (aws-cloud.html) ↗

The cloud backend is built on Amazon Web Services (AWS) using an event-driven serverless architecture. Telemetry published by the edge gateway connects via mutual TLS (mTLS on port 8883) to AWS IoT Core, where an SQL-based Rules Engine routes messages into Amazon DynamoDB for time-series persistence and triggers AWS Lambda for automated anomaly detection and reverse actuation down to the field hardware.

Figure 6. AWS IoT Cloud Operations Console Overview (Designed Cloud Dashboard). Live fleet telemetry indicators (Messages Ingested, Active MQTT Devices, DynamoDB Record Count, Lambda Alerts, and Average Ingestion Rate), active service status indicators, and the interactive 5-tier pipeline topology.

Active SQL rule (SELECT device_id, temp, humidity, pressure, vibration, battery, timestamp() AS ingest_time FROM 'iot/telemetry/+' WHERE temp > 0) evaluating incoming payloads, dispatching PutItem writes to DynamoDB, and invoking Lambda alerting on temp > 30.0°C.

7. Mobile Application (Tier 5) Architecture & Presentation

📱 Launch Interactive Mobile App Workbench (app.html) ↗

The presentation layer bridges field hardware telemetry and cloud intelligence directly to end users. In this project, the presentation tier was implemented around the IoT Sense Android Mobile Application (app.html) designed for ergonomic touch-first field monitoring and climate actuation, complemented by the Web Operations Center (dashboard.html).

Figure 9a. IoT Sense Mobile App — Real-Time Telemetry Dashboard. Featuring dynamic radial SVG gauge (temperature with color-coded warning arc), node selection chips, humidity/RSSI telemetry pills, and live BLE/AWS connectivity status indicator.
Figure 9b. IoT Sense Mobile App — Smart AC Climate Control Interface. Rotary setpoint dial (16°C–30°C target), 4-mode segmented control (Cool, Heat, Fan, Dry), 4-stage fan speed slider, and closed-loop auto-cooling threshold toggle (>26.0°C).
Figure 9c. IoT Sense Mobile App — Active Autonomous Cooling State. Real-time visual feedback with glowing cyan aura and animated compressor indicator when the temperature alert triggers automated reverse-actuation down to the field relay.
📱 Clean Architecture & MVI Pattern

Constructed in Kotlin 1.9+ and Jetpack Compose utilizing Unidirectional Data Flow (UDF). Composable functions observe an immutable TelemetryUiState emitted via Kotlin Coroutines StateFlow. Prevents race conditions across parallel telemetry streams.

⚡ Dual-Path Ingestion Pipeline

Combines a sub-50ms streaming path (Paho MQTT over WSS on port 443 with Cognito STS SigV4 tokens) for live radial gauges and actuation, with an on-demand historical query path (Retrofit2 HTTPS to API Gateway / DynamoDB) for 24h trendlines.

❄️ Smart Hysteresis AC Cooling Loop

Dual-threshold supervisor activates cooling when \(T \ge 26.0^\circ\text{C}\) and disengages when \(T \le 24.0^\circ\text{C}\). Eliminates rapid mechanical relay chatter, supported by optimistic switch UI states and a 3.5 s rollback timeout safety watcher.

8. End-to-End Zero-Trust Security Architecture

Zero-Trust Model

Security in production IoT cannot be bolted on as an afterthought or confined to a single tier. The system enforces defense-in-depth across the physical, link, transport, cloud identity, and application presentation layers.

Architecture Layer Cryptographic Mechanism Key Standard & Length Threat Vector Mitigated Implementation Details
1. Perception Hardware Flash Encryption & Secure Boot v2 AES-XTS 256-bit + RSA-3072 Physical memory dumping, malicious firmware tampering. ESP32 eFuse OTP registers burned; firmware signed with private RSA key.
2. Southbound Proximity BLE 5.0 Link-Layer Encryption AES-128 CCM (Cipher Block Chaining) Over-the-air RF sniffing, replay attacks, man-in-the-middle (MITM). BLE Secure Connections pairing; randomized advertising address rotation.
3. Northbound Transport Mutual TLS (mTLS on Port 8883) X.509 RSA-2048 / ECC SECP256R1 + SHA-256 Rogue gateway spoofing, traffic interception, DNS hijacking. Per-device client certificate & private key signed by Amazon Root CA 1.
4. Cloud Authorization Least-Privilege AWS IoT Policy AWS IAM Policy Evaluation Engine Privilege escalation, unauthorized topic publication/subscription. Thing-scoped policy restricts iot:Connect to unique client ID and iot/* topics.
5. Mobile Client Auth Amazon Cognito Federated Identities OpenID Connect (OIDC) + AWS STS SigV4 Embedding permanent AWS secrets in distributed mobile APKs. Exchanges Cognito token for 60-minute short-lived STS credentials for WebSocket upgrade.

9. Data Schema Contracts & Multi-Tier Wire Formats

Wire Specifications

To maintain zero deserialization crashes across heterogeneous hardware (C++ embedded MCU, Python gateway, AWS JSON, and Kotlin Android), the system enforces deterministic schema contracts at every tier boundary.

1. Perception → Gateway (12-Byte Packed Binary Struct)

struct __attribute__((packed)) TelemetryFrame { uint8_t node_id; // 1 byte: Node numeric index (1-3) int16_t temp_c_x10; // 2 bytes: Temp * 10 (e.g. 254 = 25.4°C) uint16_t hum_pct_x10; // 2 bytes: Humidity * 10 (e.g. 582 = 58.2%) uint16_t pres_hpa; // 2 bytes: Barometric pressure in hPa int16_t vib_mg; // 2 bytes: Kinetic vibration in milli-g uint8_t battery_pct; // 1 byte: LiPo percentage (0-100) uint16_t crc16; // 2 bytes: Frame checksum }; // Total payload = Exactly 12 bytes

2. Gateway → AWS IoT Core (Normalized MQTT JSON)

{ "device_id": "sensor_node_01", "timestamp": 1775736042, "temp": 25.4, "humidity": 58.2, "pressure": 1013.25, "vibration": 0.042, "battery": 94, "rssi": -64, "actuator_state": { "relay": false, "fan_pwm": 0, "led_mode": "BLINK" } }

12. Phased System Bring-Up Checklist & Course Milestones

Summative Milestones

To systematically bring up the end-to-end IoT demonstration system without cascading multi-tier debugging issues, engineering teams and students must follow this rigorous 5-stage sequential verification checklist spanning Weeks 1 through 8:

Phase 1: MCU Hardware & Sensor Bus Bring-Up WEEKS 1–2
  • Flash main.cpp using esptool.py --port /dev/ttyUSB0 write_flash.
  • Verify 115200 baud UART serial monitor boots FreeRTOS SMP kernel on both cores.
  • Execute automated I²C bus sweep: verify ACK received from MPU6050 at 0x68 and BME280 at 0x76.
  • Measure oscilloscope rise time on SDA/SCL: confirm \(t_r < 300\,\text{ns}\) with 4.7kΩ pull-ups.
  • Verify BLE 5.0 advertising frames using Nordic nRF Connect mobile application.
Phase 2: Gateway Ingestion & Buffer Verification WEEKS 3–4
  • Verify Linux BlueZ Bluetooth subsystem is active (systemctl status bluetooth).
  • Launch gateway_daemon.py: observe automated BLE connection & GATT subscription.
  • Verify binary BLE packet decoding into valid JSON telemetry objects.
  • Network Partition Test: Disconnect gateway WAN interface; verify telemetry records divert into local SQLite store-and-forward table (iot_buffer.db).
  • Reconnect WAN: verify accumulated records flush upstream to cloud in FIFO sequence.
Phase 3: AWS Cloud Pipeline & Security Validation WEEKS 5–6
  • Validate X.509 device certificate, private key, and Amazon Root CA1 on gateway host.
  • Test mTLS handshake to AWS IoT Core custom endpoint over port 8883.
  • Verify MQTT ingestion under topic namespace iot/{device_id}/telemetry.
  • Inspect DynamoDB table: confirm record insertion latency < 15 ms with valid partition/sort keys.
  • Verify AWS Lambda rule execution and CloudWatch log output on payload evaluation.
Phase 4: Mobile App & Reverse Actuation Validation WEEK 7
  • Launch Android Mobile App (app.html) and Web Operations Dashboard (dashboard.html).
  • Verify real-time SVG radial gauges and streaming sparklines update synchronously via WebSocket.
  • Trigger reverse control command: toggle SSR Relay (GPIO 23) from mobile switch.
  • Verify downlink MQTT command route: Cloud → Gateway → BLE GATT Write → Physical Relay.
  • Benchmark round-trip actuation latency: confirm sub-200 ms end-to-end turnaround.
Phase 5: Fault Testing & Summative Assessment WEEK 8
  • I²C NACK Fault: Disconnect SDA pin; verify firmware logs 0x02 timeout and recovers.
  • Thermal Runaway: Inject >30°C temperature anomaly; verify AWS Lambda triggers automated AC cooling within 2 seconds.
  • Vibration Shock: Inject >0.6g accelerometer spike; verify high-priority security alarm toast dispatches.
  • Summative Verification: Present live hardware demo to Professor Liang Li against course rubric.
